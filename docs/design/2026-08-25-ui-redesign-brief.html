compy Design Brief

Everything you need to design compy's five surfaces in Claude Design. The facts here are the running product — real data shapes, every action, real latencies. Your screens become the spec; they get implemented pixel-exact and verified by clicking, not by screenshots.

What compy is

A macOS menu-bar app (plus a window and CLI) that runs a local OpenTelemetry Collector for a developer. Apps on the machine send telemetry to compy; compy forwards it wherever the active configuration says. The whole product is: see what's running, switch what telemetry does in seconds, edit configurations comfortably.

Audience: developers who live in terminals. The current UI direction ("dense utility": mono type, tables, quiet text actions, amber only for the active thing) was your pick — keep it, evolve it, or replace it. The look is yours now; this brief only fixes what the screens must do.

Product truths that shape every screen

  • Exactly one configuration is active. Activating another one restarts the collector: takes 1–10 seconds, can fail. Design the in-between moment (progress) and the failure moment (see error model).
  • A configuration is a YAML document plus: named value sets (see vocabulary), an optional source URL it was fetched from, and an optional pinned collector binary.
  • Variables: writing ${env:API_KEY} in the YAML creates a variable; a comment on the same line becomes its description; :-something becomes its default. The variables UI is derived from the YAML — users don't declare variables separately.
  • Origin & protection: configurations come from three places — bundled with compy, created by the user, or fetched from a URL. Bundled ones update with compy unless the user edited them; URL ones can re-sync unless edited. Editing a protected one asks one confirmation, then it's theirs.
  • Rollback exists: compy keeps the last configuration that provably worked; one action restores it. Today it's an orphaned menu item — give it a proper home and language (e.g. "restore last working setup"), likely near collector health.
  • Slow actions: activate / restart / rollback / save-and-validate (1–10s). Everything else is instant.

Error model (design input, partly broken today)

  • User mistakes (bad name, missing field, invalid URL): short message, inline, near the cause. Never technical dumps.
  • Collector failures (config invalid, process won't start): the collector's own diagnostic text is the single most useful thing we have — it's multi-line, technical, and exactly what the user needs. Design a proper home for it (validation results, activation failures) instead of today's one-strip-for-everything.
  • bug, not design Several interactions are currently broken (activate-click, copy, delete, log search, duplicate windows). Don't design around them — they get fixed to match your screens.

The name rule, explained: configuration names become folder names on disk and CLI arguments, hence lowercase-digits-dashes. That constraint is real, but the experience is free: auto-convert while typing ("My Collector" → my-collector) instead of rejecting — your call in the design.

Empty state

Fresh installs already have the bundled configs, so the true empty state never occurs — but a "nothing active" state does. Design it: it's the first-run moment.

Screen 2 — Configuration editor

Job

Edit one configuration: its YAML, its variables and value sets, its origin and binary. You called the current layout bloated and the variables area "a mess" — this screen is the redesign's heart.

Identity & origin

  • Name: design it editable (inline rename). backend follows Rename isn't wired yet; it will be built to match your design.
  • Origin: for URL configs — the URL (editable), sync state, sync / discard-and-resync. For bundled — update-protection state. For user-owned — nothing to show, don't invent chrome.
  • Collector binary: optional override, defaults to the global choice. Low-importance control.

Variables & value sets — the hard problem

Data shape: N variables (name, description, default) × M named value sets, one set active. Typical: 2–6 variables, 1–3 sets. Operations: edit values, add / rename / delete a set, choose the active set. Cells hold secrets (API keys) — consider masking.

The current matrix-of-inputs failed. Honest options to explore (pick your own): one set visible at a time with a set switcher; master–detail (sets left, values right); or value sets as first-class cards. Nothing constrains you to a table.

YAML

  • Code editor (syntax highlight, line numbers) — component exists, style is yours.
  • Protection flow for bundled/URL configs: read-only until an explicit unlock with one plain confirmation ("future updates will keep your version" / "editing disconnects it from its URL").
  • Save = validate with the real collector: success (small, quiet) and failure (the collector's multi-line diagnostic — give it space, mono, dismissible) both need designed homes. If active, save also re-applies (slow-action moment).

Screen 3 — Collector

Job

Is telemetry flowing, and what is the collector saying?

  • Status: running/stopped · active config and its value set (missing today — your feedback) · binary · listening ports.
  • Actions: restart · rollback ("restore last working setup") — rollback likely lives here.
  • Log: the collector's output. Needs working search/filter (your feedback: it's broken), error/warning visibility, and a sane refresh story (live tail? on-demand?). Log lines are long — design for horizontal overflow.

Screen 4 — Settings

Job

Manage collector binaries; a few app options. bug, not design User-added binaries currently appear unusable — they are usable; the state model just renders confusingly. Design the honest model:

  • Four known collectors (core, contrib, otlp, ebpf-profiler) exist as downloadable: one click fetches and verifies. ebpf-profiler is unavailable on macOS — show why, not just a dead row.
  • States per row: available to download · installed (+ where) · added by you (name + path). Actions: download · make default · change path · remove (added ones).
  • Add your own: name + path to a binary.
  • App options: "Show collector switcher in menu bar" toggle · "Set OTEL_* variables system-wide" toggle. That's all — ports and shell-wiring left the UI deliberately (CLI: compy env).

Screen 5 — Menu bar (optional artboard)

Native macOS menu, so design = ordering + wording, not pixels. Current contents: status (state, config, set) · ports + error/warn counts · configuration picker (inline, overflow past 10) · value-set picker (when the active config has several) · optional collector switcher · Open compy · Quit. bug, not design "Open compy" spawning a new window every time is a bug; single-window focus is the intended behavior. Sketch the menu as a text artboard if you want to reorder or reword it.

Working agreement

  • Design in claude.ai/design — one artboard per screen is plenty; rough is fine where you're undecided, exact where you care.
  • Anything this brief didn't specify is yours to decide. Where your design contradicts a "product truth" above, say so — some truths are cheaper to change than to design around.
  • Hand the finished screens back; implementation follows them exactly, and every interaction gets click-verified against a real instance before it ships.
